# 隐私升级计划

2026-10-19 · 负责人：Zhenyan · 依据：E6 隐私过滤评估（`eval/privacy-filter/`）、E4 端到端审计（含真实 DeepSeek）、
团队整合后的代码（main，PR #3 之后）。

## 0. 现状（MVP 版本已经做到的）

| 环节 | 做法 |
|---|---|
| 识别 | Presidio + spaCy 大模型 + 14 个自定义识别器（学号、电话、成绩、个人病情、中文名、加拿大证件号、生日、地址、法语） |

## 1. 云端服务商与数据存放地（MVP 前必须处理：决定 + 报告）

**问题：** 测试用的云端是 DeepSeek（`deepseek-flash`）。按 DeepSeek 的隐私政策，用户数据存储在中国境内的服务器上（以其当前
政策为准，选型前需核实）。即使是清洗过的内容，每个云端请求仍会把以下内容送到境外：问题（去掉了身份）、课程资料段落、水平标签。
健康教育场景下，这涉及安大略省对学生信息和健康信息的期望，以及学校的伦理要求。

**风险：** 去掉身份的病情描述（约 1/5 的个人病情问题识别不出来）和课程内容离开加拿大；服务商可能保留数据或用于训练。

**方案：**
1. 报告里写明：云端服务商、数据存放地、保留政策、我们发送的字段。
2. 在客户会（Jira G1-84）上请客户和教授决定服务商。候选方向：
   - 数据存放在加拿大或美国，并提供零数据保留（ZDR）或"不用于训练"承诺的 OpenAI 兼容服务；
   - 或者 MVP 阶段只用本地模型（`.env` 里不配置云端即可，程序会自动退回本地并提示）。
3. 代码不用改：服务商由 `.env` 的 `CLOUD_BASE_URL` / `CLOUD_API_KEY` / `CLOUD_MODEL` 决定。注意推理模型要留足 token
   （`llm.cloud.max_tokens: 2000`）。

**工作量：** 半天（报告 + 会议材料）。**验收：** 报告中有"服务商与数据存放地"一节；客户的决定记录在 Jira G1-84。

## 2. 老师上传的资料会原样发往云端（建议 MVP 前做，约半天）

**问题：** 发送前的泄漏检查只扫学生的问题，不扫课程资料段落（设计如此：资料里本来就有作者名、"Cohen's kappa"这类人名术语）。
如果老师上传的材料里有真实学生名单、病例里的真实病人姓名或学号，这些内容会作为"课程资料"随云端请求发出去。

**方案：**
1. 上传时（`backend/app/admin/materials.py` 建索引之前）用隐私过滤扫一遍资料全文。
2. 发现姓名（排除已知术语和课程员工）、学号、邮箱、电话、病历号等 → 在老师后台显示警告，列出位置；
   老师可以选择"仍然使用"或"修改后重新上传"。
3. 可选：被标记的资料加上 `metadata["cloud_ok"] = False`，`build_cloud_request` 不把这类段落发往云端（本地回答仍可使用）。
4. 测试：上传一份带虚构学生名单的文件 → 出现警告；该段落不会出现在 E4 记录的云端请求里。

**工作量：** 约半天（扫描 + 后台提示 + 测试）。

## 3. 留在本地的病情问题，存储的回答里仍可能出现病情词（MVP 后，约 2 小时）

**问题：** 病情问题由本地模型回答，存储前会把这次识别到的 PII 换成占位符（不区分大小写，按整词替换）。但识别出的片段
有时比病情词长（比如识别的是"my inhaler"），本地回答里单独出现的"inhaler"或读数"150/95"就不会被替换。
这些内容存在本机数据库的会话历史里，和学生账号关联（E4 `--e6` 发现 5 例）。

**方案：** `redact_known` 对 `HEALTH_DETAIL` 片段再拆出其中的病情词和读数，分别替换；或者病情问题的回答在会话历史里只存
"[local answer to a personal health question]"。加一个测试：问"I use my inhaler before running"，存储的回答里没有"inhaler"。

## 4. 多轮追问逐条过滤（MVP 后，约 1 天）

**问题：** 过滤器一次只看一条消息。"My mom was just diagnosed." 之后接一句 "It's type 2 diabetes. What should she eat?"，
第二句单看没有个人信息，于是会去掉身份后上云（E6 多轮组 4/21 漏检）。

**方案：** 判断"是否含个人病情"时，把同一会话里最近一到两轮学生的发言（已清洗）一起看；任一轮有个人病情，本轮
`cloud_safe = false`。只影响"走不走云端"的判断，不改替换逻辑。用 E6 多轮组（8 段对话）验收。

---

## 5. 病情识别率（等客户决定后再做）

**现状：** 规则在自由书写的问题上约 75% 能认出个人病情（留出集 v2）。

**可选升级：**
- **C5：本地 Qwen 二次检查**，只对要发往云端的问题做。留出集上病情上云从约 1/5 降到约 1/8，误屏蔽 0，每次云端请求多约
  0.6 秒。评估代码已有（`eval/privacy-filter/run.py` 的 `a4_rules_llm`），需要接入发往云端的关口。
- **H2：假设化改写**——**10/20 教授同意后已启用**（`config.yaml`：`privacy.health_detail_policy: generalize`）。
  回答质量最好（4.47/5）。真实 Qwen 实测（`eval/privacy-filter/results/generalize.md`）：主集 61 个个人病情问题中 60 个、
  留出集 80 个中约 86–91% 改写成功并上云，其余留本地；通过检查的改写里残留身份信息 0 条。
  启用时补了两道检查：改写里不能重复原问题里识别出的身份信息（姓名、学号、邮箱、电话、成绩），也不能出现成绩；
  "具体数字"规则改为只拦读数、剂量、日期等，放行病名里的数字（type 2、GLP-1）。
  已知问题：少数改写会添加原文没有的细节（例如凭空加上"2 型糖尿病"），影响回答准确性，不影响隐私。

**决定点：** 客户会上确认能接受的残余风险。如果要求更严，先做 C5（约 1–2 天，含测试和 E6 复测）。
