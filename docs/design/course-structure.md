# Z1: Course structure and interface contract

Status: **decided** (2026-11-04, Zhenyan Xing). Owner: Z. Read together with
[../v4-implementation-guide.md](../v4-implementation-guide.md) (rules, owners, tasks) and
[api-v2.md](api-v2.md) (the HTTP API).

This document says how "course" enters every part of the system: what a course is, who can do what,
how students get accounts, how learner data, settings, content, materials and conversations are scoped,
what the database looks like, and how the v3 data is migrated. Agents implementing Z3, Z4, Z5, Z9, Z10,
S4, S8, S9, T6 and T7 follow it.

## 1. Decisions

| ID | Question | Decision |
|---|---|---|
| A1 | What is a course? | **One persistent course** (code + title). It is reused every year: at the end of a term the instructor ends the term (export, then the students' data is deleted, section 4.4), and next year imports new students. No per-term copies. |
| A2 | How many levels? | **Two levels: course → module.** Knowledge components (KCs) belong to the course and optionally to one module. A deeper, dynamic tree is possible later (a `parent_id` column on `module`), but is not built now: it would complicate retrieval scoping, the dashboard editor and per-module statistics. |
| A3 | What does a student pick? | **The course** (shown as code + title, e.g. "ELG 5902 – ..."), then optionally a module. The question is answered over the whole course when no module is chosen; course logistics questions (deadlines, grading) always use the course-level materials. This replaces the v3 "topic picker". |
| A3b | Same person in two courses? | Identified by the **uOttawa e-mail** on the account: one account per e-mail, one membership row per course. |
| A4 | Course-level materials (syllabus, project requirements, templates) | `material.module_id` is nullable; null = course-level. |
| A5 | KC identifiers | Surrogate integer ID in the database + a `code` unique within the course (e.g. `HBP.1`) shown to instructors. |
| A6 | YAML content files | Kept as **import/export** format (seed the demo course, offline review). The database is the source of truth. |
| A7 | MedlinePlus pages | They are the **simulated course material** of the demo course; real course material comes later. No shared "reference library" feature. |
| B1 | Accounts | One account per person, kept by the system. Memberships are removed when the course term ends. |
| B2 | Cross-course pseudonyms | **Not needed.** Learner data uses the account's random `student_id` plus `course_id`. |
| B3 | Roles | System roles: **`admin`** (everything an instructor can do, plus manage instructor accounts and system settings) and **`instructor`** (creates courses, manages own courses), and **`student`**. |
| B4 | Teaching assistants | **No TA role.** A TA uses the instructor's account for that course (trade-off in section 3.4). |
| B5 | Student import | **CSV import**; the username is the **prefix of the uOttawa e-mail** (`jdoe123@uottawa.ca` → `jdoe123`). |
| B6 | Initial password | A student who already has an account keeps it (same password). A new student activates the account with the **course invitation code** (section 3.3). |
| B7 | Matching on import | By e-mail (and therefore username); an existing account only gets a new membership row. |
| C | Settings | No restart for any setting: values apply on the next request, components are switched live in every process; the row is locked (423) until the change is fully applied or rolled back; versions, optimistic locking, history and undo, per-request snapshot, version-keyed cache (section 6). |
| D1 | Learning preferences | **Global** per student (not per course). |
| D2 | Consent | **Global** per student. The per-course visibility mode is acknowledged with one timestamp on the membership (section 5.3), not with a second consent. |
| D3 | Onboarding and diagnostic | **Per course.** Check items come from the instructor (uploaded with the course content) or are generated by the AI model connected to the course, and are edited in the instructor dashboard. |
| D4 | Visibility switch | `course_member.visible_since`; the individual overview shows only data after it. |
| D5 | Deleting data | Only **per course**: a student can delete his data in one course; ending a term lets the instructor download an export, then deletes all student data of that course. |
| D6 | Changing or removing a KC | Soft delete (`status = retired`); IDs never change. |
| E | Review of content | Content the instructor creates or uploads **counts as reviewed**. AI-generated content is a draft until the instructor publishes it. The v3 setting `content.serve_unreviewed` and the `reviewed_by` workflow are removed. |
| F1 | File layout | `courses/<course_id>/materials/<module_id or _course>/<file>` in the data volume; the database stores the path and status. |
| F2 | Rebuilding the index | After an upload or delete, the worker rebuilds the course index and increments `index_version`. |
| F3 | Where the index lives | **On disk** (`courses/<course_id>/index/v<N>/`). The api loads it on first use and keeps a small in-memory cache keyed by `(course_id, version)`. |
| G1 | Course in the URL | Yes: `/api/v2/courses/{course_id}/...` (api-v2.md). |
| G2 | Conversations | Belong to **student + course**; history is only used within the same course. |
| G3 | Logs and statistics | Every row has `course_id`; all statistics are per course. |
| G4 | API version | **`/api/v2` is defined now** (api-v2.md); `/api/v1` is frozen. |
| G5 | Fakes | Each interface ships a fake implementation in its own module (like `backend/app/llm/fake.py`). |
| H1 | v3 data | Migrated into one course, **"General Medical Knowledge"**; the five v3 topics become its five modules. |
| H2 | Database | **PostgreSQL only**, also for local tests and CI. SQLite is dropped. |
| H3 | Scale | Winter term: **2 courses × 50 students**. Design headroom: 5 courses × 150 students. |
| L | Language | No Chinese in code or in Markdown outside `docs/`; Chinese companions `*_zh.md` are allowed in `docs/` (guide rule 14). |

## 2. Concepts

| v3 | v4 | Notes |
|---|---|---|
| topic (`"high_blood_pressure"`) | **course** (`course.code` + `course.title`) | What the student picks. |
| — | **module** | A chapter or unit of the course; optional for questions. The five v3 topics become five modules. |
| KC (`HBP.1`, global by convention) | **kc** (`id`, `course_id`, `module_id?`, `code`) | Prerequisites may cross modules, never courses. |
| item, misconception (YAML) | **check_item**, **misconception** (tables) | Belong to a KC. |
| uploaded file per topic | **material** (course-level or module-level) | |
| one global config | **system settings + course settings** | Section 6. |

A course has: code, title, term label (free text, e.g. "Winter 2027", for display), course type (selects the
privacy profile), visibility mode, status (`active`, `archived`).

## 3. Accounts, roles and enrollment

### 3.1 Accounts

- `account`: `id`, `email` (unique, lower-case), `username` (unique, the e-mail prefix), `display_name`,
  `system_role` (`admin` | `instructor` | `student`), `password_hash` (Argon2, unchanged), `student_id`
  (random UUID for students, used by every learner table; unchanged from v3), `active`,
  `must_change_password`, failed-login and lock fields (unchanged).
- **Allowed e-mail domains** for import and activation: `limits.accounts.allowed_email_domains`
  (default `["uottawa.ca"]`). Accounts created by the migration or the demo seed may use `demo.invalid`.
- **Username collisions**: two e-mails with the same prefix in different allowed domains get a numeric
  suffix on the second (`jdoe123-2`). With only `uottawa.ca` allowed this does not happen.
- Identity data (e-mail, username, display name) lives **only** in `account` (v3 privacy invariant 6).
  Every other table uses `student_id` or `account_id`.
- `login_identity` (`account_id`, `provider`, `subject`) is created now with one provider (`password`), so
  that Microsoft Entra ID (OIDC) or Brightspace (LTI 1.3) can be added later without changing other tables.

### 3.2 Roles and permissions

| Action | admin | instructor | student |
|---|---|---|---|
| Create instructor accounts, reset their passwords, deactivate them | ✅ | — | — |
| System settings (default model connections, enabled course types) | ✅ | — | — |
| Create a course | ✅ | ✅ | — |
| Manage a course (content, materials, settings, members, AI tools, end term) | ✅ any course | ✅ courses where he is a member with role `instructor` | — |
| Ask questions, onboarding, own profile | — | — | ✅ courses where he is an active member |

- A course has one or more instructor members. The creator is the first; he can add other instructor
  accounts as co-instructors.
- Every course-scoped endpoint checks the role with `require_course_role` (section 9); the frontend never
  decides permissions (guide rule 8).

### 3.3 Enrollment flow

1. **Import**: the instructor uploads a CSV with a required `email` column and an optional `display_name`
   column. Other columns (for example a Brightspace student number) are ignored and never stored.
2. For each row:
   - **existing account** (same e-mail) → membership `active` right away; the student logs in with his
     existing password;
   - **no account** → membership `pending` with the e-mail (no account yet).
3. The import report lists: added (existing account), pending (needs activation), rejected (bad or
   disallowed e-mail, duplicates).
4. **Invitation code**: each course has one code (random, about 10 characters, can be rotated, has an
   expiry date; `course_invite`). The instructor shares it with the class (for example on Brightspace).
5. **Activation**: on the join page the student enters the code, his uOttawa e-mail, a display name and a
   new password. It succeeds only if a `pending` membership with that e-mail exists in that course. The
   account is created (username = e-mail prefix) and the membership becomes `active`.
6. A student who is in two courses has one account and two memberships.

**Known risk**: the system cannot check that the person who activates really owns the e-mail (there is no
e-mail sending). Mitigations: only e-mails on the imported roster can activate; the code is shared only with
the class; activation is rate-limited; the instructor can remove a membership and reset a password.
Microsoft sign-in (later) removes this risk.

### 3.4 Teaching assistants

TAs use the instructor's account (decision B4). Consequences, to be stated in the instructor manual:
the audit log cannot tell the instructor and the TA apart; the password is shared, so it must be strong and
changed after the term; a TA sees everything the instructor sees (including individual overviews in mode B).

### 3.5 End of term

`POST .../courses/{course_id}/end-term` (instructor):
1. Builds an export (ZIP of CSV/JSON): the class summary, and, only in visibility mode B, the per-student
   data of students who did not opt out. The instructor downloads it; the file is kept for a limited time
   (`limits.courses.export_retention_hours`) and then deleted.
2. Deletes, for that course: all student memberships, learner state, evidence, misconceptions, plans,
   conversations, request logs, usage counters and survey responses.
3. Keeps: the course, modules, KCs, items, misconceptions, materials, index, settings and instructor
   members. The course is ready for the next import.
4. Accounts stay. An admin can deactivate accounts that have no memberships.

**Archive** (`status = archived`) hides a course that will not run again; it requires an ended term first.

## 4. Learner data

### 4.1 Keys

Every learner table has `student_id` **and** `course_id` (decision Z1-b), except the global ones below.

| Table | Scope |
|---|---|
| `learner_kc_state` | student + course + KC (+ course-level ability row, section 4.3) |
| `evidence_log`, `learner_misconception`, `learning_plan` | student + course |
| `learner_module_level` (v3 `learner_topic_level`) | student + course + module |
| `learner_preference` | **student only** (global, D1) |
| `consent` | **student only** (global, D2) |

### 4.2 Onboarding

Per course: preferences are asked once (global); the diagnostic runs per course with the course's published
check items; a course without published items skips the diagnostic.

### 4.3 Knowledge model hooks (S8)

The course-level model keeps one ability value per student and course. Store it as a row in
`learner_kc_state` with `kc_id = null`, or in a separate table `learner_course_ability`; S8 decides and
documents it. The `KnowledgeModel` interface gains a `course_id` argument on `state` and `update`.

### 4.4 Deletion

- Student: `DELETE /api/v2/courses/{course_id}/me/learning-data` deletes his data in that course only.
- Instructor: end of term (section 3.5).
- Global data (account, preferences, consent) is not deleted by either.

### 4.5 Visibility (S9)

Fields on `course_member`:
- `hidden_from_instructor` (bool): the student opted out in mode B;
- `visible_since` (timestamp or null): when the student's data became visible to the instructor;
- `visibility_ack_at` (timestamp or null): when the student acknowledged mode B.

Rules:
- Mode B → A: `visible_since` is cleared for everyone.
- Mode A → B: `visible_since` stays null until the student acknowledges (then it is set to the
  acknowledgement time).
- The overview shows only data created after `visible_since`.

## 5. Content

- **Instructor content is published as soon as it is saved or uploaded** (decision E). This applies to
  modules, KCs, prerequisites, check items, misconceptions and materials.
- **AI-generated content** (S6, S7) is stored as `ai_draft` and is invisible to students until the
  instructor edits or accepts it; accepting copies it into the normal tables.
- **Status** on KC, check item and misconception: `active` | `retired` (D6). Retired rows stay for history
  and learner state; they are not shown or used for new questions.
- **YAML import/export** (A6): `content/topics/<topic>/{kcs,items,misconceptions}.yaml` stays as the seed
  format of the demo course. The importer maps each topic folder to a module.
- `content.serve_unreviewed` and `reviewed_by` are removed from config, code and tests.

## 6. Settings (decision C)

### 6.1 The problem

"Settings" are the values an instructor or the admin changes at run time (routing threshold, course type,
visibility mode, model connections, ...). In v3:
- every pipeline step reads the global `services.settings`;
- a dashboard change validates the new values, writes a `config_history` row, then **replaces the global
  settings object and rebuilds the learner model and the pipeline** (`services.reconfigure`);
- at startup the newest `config_history` row is applied again.

With several courses this breaks: one course's change overwrites the other's, a rebuild in the middle of
requests is fragile, and with more than one process (api and worker) a change is applied in one process
only.

### 6.2 Design

Goals: simple, cheap per request, no lost settings, **no restart for any setting on the settings pages**,
and a change cannot be submitted again until it is fully applied.

1. **Two kinds of settings.**
   - **Values** (thresholds, course type, visibility mode, usage limits, ...): passed to code that already
     exists; a new value is used by the next request in every process. Nothing is rebuilt.
   - **Components** (system settings only): the knowledge model (`bkt`, `rule`, later the course-level
     model), the optional checkers, the default routing method (`lr`, `svm`) and the default model
     endpoints. Changing one needs new objects in every process; this is done **live, without a restart**,
     as described in section 6.5. `services.reconfigure` is removed.
   - Only the pipeline step list, the database URL and secrets stay deploy-time values (they change with a
     deployment, not from a settings page).
2. **Storage**: two tables with typed columns, each with `version` (integer), `updated_at` and
   `updated_by`:
   - `system_settings`: exactly one row (admin);
   - `course_settings`: one row per course, created in the same transaction as the course; every field is
     nullable, and null means "use the system or config default".
3. **Write** (one endpoint per table, `PUT` with the `version` the client last read):
   - validate the whole new object (types, ranges, hard caps, referenced model endpoints exist);
   - in **one transaction**: update the row only if `version` still matches (otherwise **409 Conflict**, so
     two tabs cannot silently overwrite each other), increment `version`, insert a `config_history` row with
     the full values before and after, insert an `audit_log` row;
   - an invalid value is rejected; nothing is half-saved.
4. **Read** (`effective_settings(course_id)`):
   - one indexed query returns the course row and the system row together, with both versions;
   - the merged, frozen `EffectiveSettings` object is kept in a small per-process cache keyed by
     `(course_id, course_version, system_version)`; it is rebuilt only when a version changes;
   - cost per request: one primary-key query (well under a millisecond) and a dictionary lookup, against
     answers that take seconds. No time-based expiry, no notifications between processes: every process
     sees a change on its next request because the version in the database changed.
5. **Snapshot**: `ctx.settings` is built once per request and never changes during it. A background job
   stores the two versions it started with and uses that snapshot to the end.
6. **Merge order**: course value → system value → `config.yaml` default, then clipped to the `limits` hard
   cap. Layer-1 constants (required checkers, `log_raw_text`) are not settings at all.

### 6.3 Stability and not losing settings

- **The database is the only run-time store.** No change lives only in memory; a restart or a new container
  reads the same rows.
- **`config.yaml` changes at deploy time never overwrite stored values**: the tables hold only overrides,
  so a new default applies where nothing was set.
- **A stored value that becomes invalid after a deploy** (cap lowered, option removed) is clipped or ignored
  with a warning in the log and a metric; requests do not fail. The settings page shows the adjusted value.
- **`config.yaml` is validated at startup**; an invalid file stops the app with a clear error instead of
  running with bad defaults.
- **History and undo**: every change is in `config_history`; `POST .../settings/restore/{history_id}` writes
  an earlier version back (as a new change, also audited).
- **Schema changes** go through Alembic migrations that carry the data (a renamed column is copied, never
  dropped and re-created empty).
- **Model endpoints**: deleting an endpoint sets the references to null (falls back to the system default)
  and is audited. API keys are encrypted with `SETTINGS_ENCRYPTION_KEY` from the environment; the app does
  not start without it when encrypted keys exist. Saving an endpoint requires a successful connection test.
- **Ending a term or archiving a course** does not touch its settings.
- **v3 migration**: the newest v3 `config_history` row is copied (routing threshold and progress display →
  the demo course; checkers, weak evidence and level thresholds → `system_settings`; local model URL and
  model → a `model_endpoint` set as the system default). Nothing set in v3 is lost.

### 6.4 Fields

`course_settings` (instructor of the course; all nullable):

| Field | Type | Default when null | Used by |
|---|---|---|---|
| `course_type` | `medical_science` \| `life_science` \| `ece` \| `general` | `general` | privacy profile, checkers, disclaimer |
| `visibility_mode` | `A` \| `B` | `A` | S9 |
| `local_only` | bool | false | route, generate, instructor AI |
| `routing_preference` | `default` \| `prefer_local` \| `prefer_cloud` | `default` | route |
| `routing_threshold` | float 0–1 | config | route |
| `show_routing_progress` | bool | config | ask stream |
| `local_endpoint_id`, `cloud_endpoint_id` | model endpoint | system default | model gateway |
| `usage_questions_per_minute`, `usage_questions_per_day`, `usage_cloud_calls_per_day` | int | config | usage check (not shown in the UI yet, guide 4.4) |

`system_settings` (admin; all nullable except the version):

| Field | Default when null | Used by |
|---|---|---|
| `default_local_endpoint_id`, `default_cloud_endpoint_id` | the endpoints from `.env` / `config.yaml` | model gateway |
| `enabled_course_types` | all | course creation form |
| `checkers` (optional ones only, e.g. `grounding`) | config | verify (required checkers are always added) |
| `weak_evidence`, `level_basic_below`, `level_advanced_above`, `level_hysteresis` | config | learner |
| `knowledge_model` (component) | config | learner (section 6.5) |
| `default_routing_method` (component) | config | route (section 6.5) |

Fields marked *component* need the live switch of section 6.5; the endpoint and checker fields are
components too. Changing `course_type` is allowed and audited; it affects only later questions.

### 6.5 Applying a change, and the lock until it is fully applied

Each settings row (`system_settings`, every `course_settings`) has an apply state:
`apply_state` (`applied` | `applying` | `failed`), `apply_target_version`, `apply_started_at`,
`apply_error`.

**Lock**: while a row is `applying`, every `PUT` and `restore` on that row is refused with
**423 Locked** (`code: settings_applying`), and the settings page disables its Save button and shows the
progress. The server enforces it, so a second tab or a double click cannot start a second change. The lock
is released when the change is fully applied, has failed, or has timed out.

**Value changes** (course settings and system value fields): the transaction that saves the row sets
`apply_state = applied` directly. Every process reads the new version on its next request (section 6.2),
so the change is fully applied when the save returns. The Save button is disabled while the request runs.

**Component changes** (system settings only):
1. The save transaction stores the new values, increments `version`, and sets `apply_state = applying`.
2. Every process (each api and worker container) runs a small background loop every
   `limits.settings.poll_seconds` (default 5 s): it writes its heartbeat to `process_status`
   (`process_id`, `kind`, `last_seen`, `component_version`, `error`) and reads the system row's version.
3. When the version is newer than the process's component set, the process **builds a new component set in
   the background** (for example loads the other knowledge model or connects to the new endpoint) while it
   keeps serving with the old set. When the new set is ready, it **swaps one reference**. Requests that
   already started finish with the old set; new requests use the new one. The process then reports
   `component_version = target`.
4. The change is **fully applied** when every live process (heartbeat within `3 x poll_seconds`) reports the
   target version. Then `apply_state = applied` and the lock is released.
5. **Failure**: if a process cannot build the new set, it keeps the old one and reports the error. If any
   process fails, or not all are ready within `limits.settings.apply_timeout_seconds` (default 120 s), the
   change is **rolled back**: the previous values are written back as a new version, the processes that
   already switched build the old set again, and `apply_state = failed` with the reason. The lock is
   released and the page shows the error.
6. **Restarts**: a process that starts while a change is applying builds the target set directly. A process
   that stops sending heartbeats is no longer counted after `3 x poll_seconds`.

Cost: one tiny query per process every 5 s, plus the build itself only when a component changes. Request
handling is not slowed down and never waits for a build.

**Learner data and the knowledge model**: all knowledge models read and write the same `learner_kc_state`
columns, so switching between them keeps every student's state.

## 7. Materials and index

- Layout in the data volume (`DATA_DIR`, default `/var/app`):

  ```
  courses/<course_id>/materials/_course/<file>
  courses/<course_id>/materials/<module_id>/<file>
  courses/<course_id>/index/v<N>/
  courses/<course_id>/exports/<export_id>.zip
  ```

- **Upload**: stored, then `scan_document()` (Z11) runs, then a `job` rebuilds the course index (F2). A failed
  scan or parse is shown in the dashboard with the reason (as in v3).
- **Index** (F3): written by the worker to `index/v<N+1>/`. `index_version` is then incremented. The api
  loads the new version on the next request and drops the old one from its cache. Old versions are deleted
  by the worker after a short delay.
- **Demo course**: the MedlinePlus snapshots in `data/medical_rag/` become materials of "General Medical
  Knowledge" (one module each), A7.

## 8. Conversations, logs, statistics

- `conversation` (`id`, `student_id`, `course_id`, `created_at`); `session_turn` gets `conversation_id`.
  History sent to the models comes only from the same conversation, so never from another course (G2).
- `request_log`, `survey_response`, `usage_counter`, `audit_log` and `config_history` have `course_id`
  (null only for system-level actions). The class summary, logs and survey summary are per course (G3).
- `privacy.log_raw_text` stays false; nothing in this section stores question text.

## 10. Database (PostgreSQL)

- **PostgreSQL only** (H2): local development uses the `db` service of `docker compose`; tests create a
  temporary database per test session (a pytest fixture; CI adds a `postgres` service container). SQLite and
  its special cases (`as_utc` for naive datetimes) are removed.
- **Migrations**: Alembic in `backend/alembic/`; every schema change is a migration; CI runs
  `alembic upgrade head` on an empty database before the tests.
- **Tables** (in addition to section 3–8 fields):

| Group | Tables |
|---|---|
| Identity | `account`, `login_identity`, `auth_session` |

## 11. Migration from v3 (Z3, Z4)

1. Create the course **"General Medical Knowledge"** (code `MED 0000`, type `medical_science`, visibility
   mode A) with five modules from the v3 topics, in the v3 order.
2. Import `content/topics/*/` YAML into its KCs, items and misconceptions (KC codes unchanged).
3. Copy accounts from the v3 SQLite database. Accounts without an e-mail get `<username>@demo.invalid`.
   The v3 instructor (`prof`) becomes an `admin`.
4. Copy learner state, evidence, misconceptions, consent and preferences with `course_id` of the new course;
   `learner_topic_level` rows map to `learner_module_level`.
5. Copy request logs and survey responses with the new `course_id`; session turns become one conversation
   per v3 session.
6. Register the MedlinePlus snapshots as course materials (section 7) and build the index.
7. The script is idempotent and refuses to run on a non-empty target database.

## 12. Scale (H3)

Winter term: 2 courses × 50 students. Assume up to 20 students asking at the same time during a class
session. This is the input for Z2 (vLLM sizing) and for the default usage limits. PostgreSQL and one api
container handle this easily; on-disk indexes for 2–5 courses fit in memory when loaded.
