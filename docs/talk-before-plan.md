## 1. 课程化：以整门课程为单位，健康课做示例，另加一门工程课验证兼容性

**决定**：仍以健康内容做示例，但示例是**一整门课**，不再是一个个健康问题；另加一门工程课，验证系统对其他课程的兼容性。

**结构**：课程 → 主题（章节）→ 知识点（KC）。

| 示例课程 | 内容 | 验证什么 |
|---|---|---|
| 健康课（例如"慢性病基础"） | 现有 5 个主题作为 5 个章节；补教学大纲、项目要求、提案模板、期中/期末汇报模板（PPT）、讲义（PDF）。内容自写或使用有授权的材料 | 整门课的资料流程；学生能问课程事务问题（"期中汇报什么时候交、要包含什么"） |
| 工程课：**ELG 5902**（已决定） | 教学大纲、项目要求和交付物、MVP/Beta 要求文档、汇报模板（先征得 Gita 教授同意）；课程类型选"电气与计算机工程" | 换领域后隐私过滤、路由、检索、个性化是否仍然正常；同时这也是客户最关心的"项目要求、模板类"资料 |

**工程课上预计的风险**（即兼容性测试要测的）：
1. 隐私过滤误遮挡工程术语（"stress test"、"pressure 150/95 kPa"、"failure"、"load"）。由第 2 节的分学科过滤解决，并用工程问题集测误遮挡率。
2. 路由模型用健康问题训练，工程问题可能全部被判为训练范围外而送云端。需要用工程问题评估，可能要补训练数据（Tongkai）。
3. 医疗相关的提示和检查（"不是医疗建议"、`medical_safety`）要按课程类型开关；现在 `medical_safety` 是必选（`runtime_config.py` 的 `REQUIRED_CHECKERS`）。

## 2. 隐私模块按学科切换（Zhenyan 新提出）

**想法**：教师建课程时选择课程类型（例如计算机/软件工程、土木工程、生命科学），系统据此启用对应的过滤规则；以后接手的团队可以方便地加新的课程类型。

**设计：基础层 + 学科档案（privacy profile）**

- **基础层（所有课程都开）**：姓名、学号、邮箱、电话、地址、出生日期、证件号、成绩，以及**通用的个人情况**。学生在任何课都可能说"我生病了能不能延期"，所以个人健康和需要特殊照顾的情况要有一个轻量的通用识别，不能只在生命科学课里才有。
- **学科档案（按课程类型叠加）**：

首批做三个档案（11-04 决定），加上默认的"通用"：

| 课程类型 | 额外识别 | 其他随档案变化的设置 |
|---|---|---|
| **医学（medical science）** | 现在完整的病情规则（`health_detail`、`health_context`、读数、跨消息病情、假设性改写 `generalize`） | `medical_safety` 检查、"不是医疗建议"提示 |
| **生命科学（life science）** | 个人健康用基础层的识别；另外识别**研究参与者和样本的信息**（受试者编号、病人化名、样本编号）、实验室里的个人身份信息 | 生物学术语（物种、基因、细胞、浓度）不当作个人病情；不加医疗安全检查，"不是医疗建议"提示可选 |
| **电气与计算机工程（ECE）** | 学生贴代码时带出的**密钥、令牌、密码、私有仓库地址、内网 IP、连接字符串**；设备标识（MAC 地址、序列号）；代码里的真实姓名和邮箱 | 代码片段原样保留；电路和信号数值（V、mA、kΩ、Hz、dB）不当作个人读数 |
| 通用（默认） | 只有基础层 | — |

不做土木工程；以后需要时按下面的扩展方式加。

- **可扩展**：每个档案是一个配置文件（例如 `privacy_profiles/life_science.yaml`），列出要启用的识别器、词表、策略、检查项和界面提示。新的识别器沿用现有的"加一个文件、加一行配置"注册方式。接手团队加新课程类型 = 写一个档案文件，需要时再写识别器，并附上**这个学科自己的标注测试集**（误遮挡率和漏检率都要测）。
- **教师界面**：建课程时选择类型；课程设置页显示当前档案启用了哪些识别项（只读，参考 G1-114 计划的隐私面板）。
- **评估**：现有 E6 测试集归到"生命科学"档案；每个新档案至少有一个小的标注集，加一组"其他学科术语"的反例集，专门测误遮挡。

## 6. 教师端 AI：三档都要，再加第四档"本地模型能否胜任"的评估

**第一档：基于课程资料生成草稿**
- 项目方向和项目清单（附难度、需要的知识点、预期交付物）；
- 根据教师的模板生成示例提案或给学生的写作指南；
- 从大纲和项目要求里整理常见问题（截止日期、评分标准等）。

**第二档：搭建个性化所需的内容**
- 从讲义起草知识点、依赖关系、每个知识点的检测题和常见误解。
- 全部是**草稿**，教师确认后才对学生生效（沿用现有"草稿 → 已审核"`reviewed_by` 机制）。

**第三档：班级洞察**
- 学生集中在问哪些知识点、哪些误解出现得最多。只用知识点标签和统计数字，不显示提问原文。

**第四档（新增）：评估本地模型能否胜任这门课，并和云端模型对比**
- **对象**：都在**有 RAG** 的条件下，比较"本地模型 + 课程资料"和"云端模型 + 课程资料"。
- **流程**：
  1. 从这门课的资料生成一批测试问题，覆盖每个章节和不同难度，包括事务性问题（截止日期）和概念问题；教师可以抽查和修改。
  2. 两边分别作答。
  3. 用评审模型打分（是否正确、是否有资料依据、是否完整），教师抽样复核。
  4. 记录延迟和费用。
- **输出**：按章节和题型给出报告，例如"本地模型在第 3 章的概念题上和云端差不多，在项目设计类开放问题上明显较弱"。
- **用途**：教师据此决定这门课的路由偏好（更多走本地还是云端）；也给路由阈值的校准提供依据（Tongkai）。
- **隐私**：测试问题是生成的，不涉及学生；但课程资料会发给云端，需要教师同意。

**界面提示：数据可能发往云端（学生和教授都要看到）**
- **学生端**：
  - 入学同意书里说明：问题经过脱敏后可能发给云端模型；
  - 聊天页常驻一行简短提示；
  - 每条回答标明是本地还是云端回答的（路由过程里已经有，需要做得更醒目）。
- **教师端**：
  - 使用生成功能前提示"课程资料会发给云端模型"；
  - 课程设置里可以选"本课程只用本地模型"。

**其他注意**
- 教师上传的文件里可能有学生名单（如分组表），上传时用隐私过滤扫描（`隐私升级.md` §2，还没做）。
- 教师端的提问不走学习者个性化，也不写入学习者模型。

## 7. 学生个人概览：每门课程由教师选择可见性方案

**决定**：每门课程设一个选项，教师选择**不看**或**看**单个学生的档案；学生能看到教师选了哪种方案。选"看"时，按下面的规则执行。

**两种方案**
- **方案 A：只看班级汇总**（相当于现在的做法）。
- **方案 B：可以看个人概览**，内容包括：
  - 各知识点的掌握程度和变化趋势；
  - 检测题作答记录；
  - 出现过的误解；
  - 学习偏好；
  - 活跃程度（提问次数、最近登录）。

  教师还可以给学生**制定学习计划**：指定重点知识点或学习目标、手动调整难度、写备注。

**方案 B 的规则**
- **提问原文**：不保存（`log_raw_text: false` 不变），教师看不到学生问了什么原话。
- **知情同意**：入学同意书写明这门课采用哪种方案。
- **权限**：只有这门课的教师和助教能看；每次查看都记录。
- **透明**：学生在"What I know"页面能看到老师看到的内容和老师定的学习计划。
- **云端**：学习者档案仍然不发给云端，"档案泄露"检查继续有效。

**学生能看到方案**
- 选课程时、入学问卷和"What I know"页面都显示当前方案。

**切换方案的规则**（11-04 决定）
- **B → A**：立即生效，教师马上看不到个人档案。
- **A → B**：先通知学生，学生重新确认后才对他生效；**只显示切换之后的数据**。

**学生单独退出**（11-04 决定：加，因为不会让架构变复杂）
- 方案 B 下，学生可以选择"不让老师看我的个人档案"。
- 实现：选课记录上一个"不公开"字段；权限检查里多一个条件；教师看到的该学生只显示"该学生选择不公开"，其数据只计入班级汇总。
- 退出后教师不能给他定学习计划，个性化照常由系统自动进行。
- 学生可以随时改回公开，同样只显示改回之后的数据。

**要同步改**
- 教师面板上"Class-level data only…"这句话按方案显示；
- 隐私设计文档和报告；
- 相关测试。

## 8. 个性化：课程级的知识模型（不是单个主题，也不要纯规则）

**按讨论的方案做**：
- 按课程区分学习者状态；
- 接入教师的学习计划；
- 课程事务问题跳过个性化；
- 记录学习速度；
- 没有知识点时照常回答；
- 在工程课上重做 E3 评估。

**新增：课程级的知识模型**

一门课有 50～200 个知识点，有前后依赖。需要一个能在整门课上工作的模型，而不是每个主题各算各的。Zhenyan 不希望用纯规则模型。

| 候选 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **分层模型（推荐起点）** | 每个学生在每门课有一个**整体能力值**（类似 Elo/IRT 的评分，每次作答在线更新），每个知识点在它的基础上做 BKT 或 PFA 修正；知识点之间按依赖图互相影响（基础知识点掌握得差，后续知识点的估计也往下调） | 数据少时也能用：新知识点可以从整体能力起步，不用每个知识点从零开始；参数少，可以解释，适合给教师的个人概览 | 依赖图的影响强度要调 |
| PFA（Performance Factors Analysis） | 按做对、做错的次数做逻辑回归 | 参数少，容易用真实数据拟合 | 没有显式的"学会"过程 |
| 依赖图上的 BKT（动态贝叶斯网络） | 把依赖关系直接放进 BKT | 理论上最完整 | 计算量和调参难度随知识点数量增长 |
| 深度知识追踪（DKT / SAKT / AKT） | 神经网络序列模型 | 数据多时效果最好 | 需要大量真实作答数据，现阶段做不了；作为以后有数据时的升级方向 |

**建议**：先做"整体能力 + 知识点级 BKT/PFA + 依赖传播"的分层模型。用现有的模拟学生数据和工程课测试，再在冬季学期用真实数据拟合参数。规则模型只在模型出错时作为兜底，不作为主要模型。
**还要**：在接口里保留可以替换的位置（现有 `KnowledgeModel` 接口），以后换成深度模型时不用改其他部分。

## 9. 部署：一套完整的 Docker Compose

**决定（11-04 修订）**：整个应用设想成**一套完整的 Docker 部署**，不拆成多种云服务，`docker compose up` 一条命令启动。**vLLM 本地模型服务是单独部署的，不放进我们的 compose**；应用只通过它的 OpenAI 兼容 API 地址连接（地址和 API key 写在配置里，教师也可以在设置里改，见 9.2）。所以应用主机不需要 GPU；可以是 AWS 上的一台普通实例（区域选加拿大中部），也可以是任何服务器。

**暂不做（11-04 决定）**：数据库备份、硬盘加密。以后正式给全班使用前再考虑。

**云端模型**：之后使用 GPT、Claude 或 Cohere（由客户决定，本文件不再讨论服务商）。

### 9.1 组成

```
学生 / 教师浏览器
   │ HTTPS（443，唯一对外开放的端口）
┌──────────────────────── 应用主机 · docker compose ───────────────────────┐
│ proxy   Caddy：自动申请 HTTPS 证书，提供前端页面，把 /api 转给 api       │
│   │                                                                    │
│ api     FastAPI（现有镜像）                                             │
│ worker  同一个镜像，运行后台任务（索引、教师端 AI 生成、评估、每日用量重置）│
│   │                                                                    │
│ db      PostgreSQL（数据卷）                                            │
│ 监控    Prometheus + Grafana（可选，compose 的 monitoring 配置）         │
│ 数据卷  上传的资料、检索索引、数据库                                     │
└──────────────────────────────────────────────────────────────────────┘
   │ 只有 api / worker 能访问外网
   ├── vLLM 本地模型服务（单独部署，不在 compose 里；OpenAI 兼容 API，可信本地，可以收到原文）
   └── 外部模型 API（云端模型、教师自己的 OpenAI 兼容 API；只收脱敏内容）
```

- **两个 Docker 网络**：
  - **对外网络**：proxy、api、worker 在上面；
  - **内部网络**：设成 `internal`，不能访问外网。db 只在内部网络上；api 和 worker 两边都接。
- **只开放 443 端口**（80 只用来跳转到 HTTPS）；db、监控的端口都不映射到主机。
- **服务器登录**：只用 SSH 密钥，关闭密码登录。
- **vLLM 服务的连接**：
  - vLLM 启动时设置 API key（`--api-key`）；
  - vLLM 主机的防火墙只允许应用主机访问；
  - 如果两台机器之间要经过公网，就用 HTTPS（在 vLLM 前面加一个反向代理）。
- **本地开发**：把模型地址指向 Ollama 或任何 OpenAI 兼容地址即可，compose 不用改。

### 9.2 本地模型改用 vLLM

- vLLM 提供 OpenAI 兼容的接口，现有的 `openai_compat` 客户端基本可以直接用；它会把多个请求合并成一批来算，并发能力比 Ollama 好很多。
- 要做的：
  - 本地模型的客户端可以在 Ollama 和 vLLM 之间切换；
  - 测试 `understand` 的 JSON 输出、关闭"思考"模式这些设置在 vLLM 下是否正常；
  - 压力测试：GPU 能同时处理多少请求、排队多久，用来定第 9.6 节的上限。

**GPU 规格和模型对比**（11-04 决定）
- **默认规格**：按能跑 9B 模型（现在用的 `qwen3.5:9b` 这一级）来配置。
- **对比 27B**：通过 OpenRouter API 调用同系列的 27B 模型，用第 6 节第四档的评估方法（同一批课程问题、都带 RAG）对比 9B 和 27B 的回答质量、延迟和费用。OpenRouter 上只发生成的测试问题，不发真实学生数据。
- **费用估算**：按"同时运行 9B 和 27B 两个模型"的 AWS 硬件来算。下表是初步估计，使用美东区按需价格；部署区域选加拿大中部，价格要在 AWS 价格计算器里按加拿大中部重新核对。

| 方案 | 机器 | 显存 | 怎么放两个模型 | 约每小时 | 约每月（24×7） |
|---|---|---|---|---|---|
| A（推荐先评估） | 1 台 g6e.xlarge（L40S） | 48 GB | 9B 用 FP8（约 10 GB）+ 27B 用 4-bit 量化（约 16 GB），剩下的给并发用的缓存 | 约 1.9 美元 | 约 1,400 美元 |
| B | g6.xlarge（L4，24 GB）跑 9B + g6e.xlarge 跑 27B | 24 + 48 GB | 各占一台，互不影响 | 约 2.7 美元 | 约 1,950 美元 |
| C | 1 台 g5.12xlarge（4 × A10G） | 96 GB | 两个模型都不量化 | 约 5.7 美元 | 约 4,100 美元 |

  vLLM 单独部署，上表是 vLLM 那台 GPU 机器的费用。应用主机不需要 GPU，用一台普通实例即可，另加硬盘和流量，大约每月几十美元。
  如果 GPU 只在学期中的白天开（比如每天 14 小时、每周 5 天），GPU 费用大约降到上表的 40%。
  量化会影响回答质量，要用第四档评估确认。

**模型连接可以由教师修改**（11-04 决定）
- 系统默认连好一个本地模型（部署时配置的 vLLM），教师不用做任何设置就能用。
- 教师可以在设置里改成连接**自己部署的 OpenAI 兼容 API**（填地址、模型名、API key）。云端模型同理，默认一家，可以修改。
- 现在面板上已有"本地模型服务器地址 + 模型名 + 测试连接"（G1-94），在它的基础上扩展：
  - 支持 OpenAI 兼容格式和 API key；
  - 以后课程化之后，可以按课程设置（底层结构见 9.6）。
- **隐私边界要标清楚**：系统必须区分"可以收到原文的本地模型"和"只能收到脱敏内容的外部模型"。教师把"本地模型"改成别人的服务时，学生原文就会发到那里。设置页要明确提示这一点，并要求教师确认这个服务归他自己控制。
- **安全**：
  - **防止服务器被当跳板**：教师填的地址会由服务器去访问，必须禁止填写云平台内部地址（例如 `169.254.169.254` 这类元数据地址）和本系统内部的服务地址，否则可能被用来窃取云平台的凭证（这类攻击叫 SSRF）。
  - **API key**：加密存储，界面上只显示后几位；修改记录写进审计日志。

### 9.3 防止被攻击、窃取学生和教授隐私：程序和部署都要改

**威胁**：攻击者窃取数据库或上传的资料；学生或教师越权看别人的数据；通过上传资料或提问注入指令，让模型泄露信息；账号被盗；密钥泄露。

**网络**
- 只开放 443 端口（9.1）；数据库和模型只在 Docker 内部网络；主机防火墙（以及 AWS 安全组）只放行 443 和管理员的 SSH。

**程序**
- **越权检查（最重要）**：每个接口都要检查"这个用户能不能访问这门课、这个学生"。教师 A 不能看教师 B 的课，学生不能看别人的数据。每个接口都要有对应的测试。课程化（第 3 节）之后这一点尤其重要。
- **指令注入**：上传的资料和检索到的段落只当作资料，不能当作指令；云端请求前的泄露检查、回答后的个人信息和档案泄露检查都保留。
- **上传文件**：大小和类型限制（已有）、解压大小检查（已有）；文件解析放在有资源限制的进程里；可以考虑加病毒扫描。
- **会话**：cookie 设为 `HttpOnly`、`Secure`、`SameSite`（已有，`cookie_secure` 在公网必须为 true）；会话有过期时间（已有，12 小时）；退出和改密码时让所有会话失效；修改数据的请求加 CSRF 防护。
- **登录**：限制失败次数并暂时锁定；密码用 Argon2 哈希（已有）；教师账号加双重验证。
- **依赖和镜像**：CI 中加入依赖漏洞扫描（`pip-audit`、`npm audit`）、代码安全检查（`bandit`）和镜像扫描。

**数据**
- **加密**：对外全程 HTTPS；应用到 vLLM 之间如果经过公网，也用 HTTPS（9.1）。硬盘加密暂不做（11-04 决定）。
- **少存**：不存提问原文（已有）；日志里不出现个人信息。
- **生命周期**：规定保留期限；学生可以删除自己的学习数据（已有 `DELETE /learner/me`）；课程结束后整体归档或删除。
- **备份**：暂不做（11-04 决定），正式给全班使用前再加。
- **密钥**：放在主机上的 `.env` 文件（只有部署账号可读）或 Docker secrets 里，不进镜像、不进代码仓库。
- **权限**：云账号按最小权限分配；管理员必须用双重验证。

**审计和应急**
- 教师查看个人档案、修改设置、导出数据都记录。
- 写一份数据泄露应急流程，包括按法规通知受影响的人。
- 上线前做一次安全测试（按 OWASP Top 10 自查，或请人做渗透测试）。

### 9.4 登录：现阶段用自己的账号，预留以后接 Microsoft 等 OAuth

- **现在**：继续用自建账号（用户名 + 密码，教师创建、批量导入）。
- **预留**：把"账号"和"登录方式"分开存。新增一张登录身份表（登录方式、该方式下的用户标识 → 账号），用户名密码只是其中一种方式。以后接学校的 Microsoft 365（Entra ID，走 OIDC 协议）或 Brightspace（LTI 1.3）时，只要加一种登录方式，并把它关联到已有账号，账号、学习数据和课程关系都不用改。
- **现在就要注意**：
  - 不要把用户名当作永久标识，其他表都关联账号 ID；
  - 账号上可以预留一个可选的学校邮箱字段，以后用来匹配；
  - 登录的接口和页面写成"选择登录方式"的结构，以后加一个"用 Microsoft 登录"按钮即可。

### 9.5 数据库换成 PostgreSQL，支持多个班级和课程

- 现在用的是 SQLite，没有数据库迁移工具。改成：
  - PostgreSQL 容器（数据卷；备份暂不做）；
  - 引入 Alembic 管理表结构变更；
  - 写一个从 SQLite 导数据的一次性脚本。
- 所有和课程有关的表都带 `course_id`，访问控制在程序里统一检查。以后可以再加 PostgreSQL 的行级安全，作为第二道防线。
- 本地开发和测试可以继续用 SQLite。

### 9.6 并发和费用（重点）

**放进配置文件的设置**

现在有一部分限制直接写在代码里。建议新增一个 `limits`（或 `operations`）配置段，把下面这些集中起来：

| 类别 | 设置 | 现在在哪 |
|---|---|---|
| 本地模型（vLLM） | 同时处理的请求数、排队上限、排队超时、生成超时、最大输出长度 | 部分在 `config.yaml` 的 `llm.local`（`timeout_s`、`max_tokens`），排队没有 |
| `understand` 步骤 | 超时（现在 5 秒，截图时连续两次超时） | `config.yaml` `llm.understand` |
| 云端模型 | 超时、最大输出长度、每日总调用上限、每日费用上限 | 部分在 `llm.cloud`，上限没有 |
| 每个学生 | 每分钟、每天的提问次数，每天的云端调用次数 | 没有 |
| 上传 | 单个文件大小、PDF 页数、单个文件和单门课程的文字上限、允许的文件类型 | 写死在 `materials.py`（`MAX_BYTES`）、`documents.py`（`MAX_FILE_BYTES`、`MAX_TEXT_CHARS`、`MAX_PDF_PAGES`）、`medical_hybrid.py`（每主题 2,000,000 字符） |
| 登录 | 失败次数上限、锁定时间、会话有效期 | 会话有效期已在 `auth.session_ttl_hours`，其余没有 |
| 检索 | 返回段落数、分段长度 | 部分写死（`medical_hybrid.py` 的 `_MAX_CHARS`） |
| 隐私 | 改写长度上限 | 写死（`generalize.py` 的 `MAX_CHARS = 300`） |
| 学习者 | 摸底题数量、每次回答处理的误解数 | 写死（`checks.py` 的 `DIAGNOSTIC_MAX`、`misconceptions.py` 的 `MAX_IN_PROMPT`） |
| 汇总 | 显示问卷汇总的最少人数 | 写死（`survey.py` 的 `MIN_AGGREGATE_SIZE = 3`） |
| 管理 | 测试本地模型连接的超时、日志每页条数 | 写死（`llm_server.py` 的 `TIMEOUT_S`、`logs.py` 的 `MAX_PAGE_SIZE`） |
| 监控 | 告警阈值（见 9.7） | 没有 |

隐私和检查相关的固定值不建议让教师改，例如 `REQUIRED_CHECKERS`、`log_raw_text`，以及识别器内部的窗口长度。它们属于安全设计，放在代码或隐私档案里，不进普通配置。

**每个学生的用量放进教师界面的课程设置会不会太复杂？**

评估：**中等复杂，可以做，但建议分两步**。
- 课程设置页本来就要做（课程类型、可见性方案），在上面加几个用量字段的界面成本不高。
- 真正的工作量在后端：用量计数表、请求前的检查、每天重置，以及和全局上限的关系。这部分不管放配置文件还是放界面都要做。
- **建议**：
  - **第一步**：配置文件里设全局默认值和硬上限，所有课程统一。
  - **第二步**：课程设置页允许教师在硬上限以内调整本课程的值，并显示本课程的用量统计（只显示汇总，或者按第 7 节的方案显示）。

**决定（11-04）**：先做第一步，但**现在就把"每门课程有自己的设置"的底子打好**：
- **一张课程设置表**：每门课一行，每个可以按课程调整的设置一列，**允许为空**；为空表示"用配置文件里的默认值"。课程类型、可见性方案、模型连接、用量限制都放这里。
- **一个统一的取值函数**：程序里需要某个设置时，都通过"课程设置有值就用课程的，否则用配置文件的，最后再按硬上限截断"这一个函数来取，不在各处直接读配置文件。
- **硬上限只在配置文件里**：教师以后能改的值也不能超过它。
- 这样第一步时课程设置表里的用量字段全部为空，行为和"全部用配置文件"完全一样；以后做第二步只需要加界面，不用改表结构和业务代码。
- 用量计数从一开始就按"学生 + 课程 + 日期"记录，第二步要显示每门课的用量时可以直接用。

### 9.7 监控（整个系统）

- **指标**：
  - 每一步的耗时和失败率（流水线本来就记录了每步的耗时）；
  - 本地和云端的调用量、排队长度、超时次数；
  - GPU 使用率和显存；
  - 云端费用；
  - 登录失败次数；
  - 数据库连接数和磁盘。
- **工具**：Prometheus + Grafana，作为 compose 里可选的 monitoring 配置一起部署；应用和 vLLM（vLLM 自带）都暴露 `/metrics` 接口，供 Prometheus 定期读取。
- **告警**：服务宕机；错误率超过阈值；排队过长；当天云端费用接近上限；登录失败异常增多（可能有人在暴力破解）；隐私检查拦截量突然上升。
- **日志**：结构化日志，不含提问原文和个人信息；规定保存期限。
- **健康检查**：现有的 `/health` 扩展为检查数据库、vLLM 和云端模型是否可用。

## 16. 系统架构 v4（草案）

v3.1 是"一个班、5 个健康主题、一台服务器"的架构。v4 要支持多门课程、多个教师、按学科切换隐私规则、教师端 AI、公网部署。本节是 Z1 设计文档的起点。

### 16.1 重写还是改造：建议**以改造为主，局部重写**

**现有代码规模**：后端约 8,600 行，测试约 5,400 行（620 个测试），前端约 5,700 行。

**不建议整体重写**，原因：
1. **主干设计能直接沿用**。处理流程由配置文件列出的步骤组成，路由、检索、知识模型、检查项都通过注册表按名字选择，这正是 v4 需要的扩展方式。v4 的新需求大多是"加东西"，再加上一个贯穿全局的"课程"维度，不需要推翻主干。
2. **隐私过滤是验证过的资产**。E6 五个测试集、E4 审计的结果都对应现在的代码；重写意味着这些评估要重做。
3. **时间不够**。到 12/13 只有 5 个多星期，重写加上补回 620 个测试，留给新功能的时间会非常少。

**但有几块要重写**，因为它们的前提（一个班、全局设置、YAML 内容、SQLite）变了，而且这几块本身都不大：

| 模块 | 现状 | 处理 | 原因 |

所以 v4 用一个新的长期分支，按 Z1 → Z3 → Z4 的顺序逐步改造，每一步都保持现有测试通过。

### 16.2 设计原则

1. **课程是数据和权限的边界**：几乎所有数据都属于某门课程；每个接口先确认"这个用户在这门课里是什么角色"，再做事。
2. **隐私边界写进架构**：每个模型连接标明是"可信本地"（可以收到原文）还是"外部"（只能收到脱敏内容），模型网关强制执行，不靠每个调用的地方自觉遵守。
3. **设置分层，统一取值**：代码里的安全常量 → 配置文件的默认值和硬上限 → 环境变量和密钥 → 课程设置。全部通过一个取值函数读取。
4. **扩展靠注册，不改主干**：新的隐私档案、识别器、检索器、知识模型、检查项、处理步骤、模型后端，都通过"加文件 + 加配置"接入。
5. **长任务放到后台**：资料索引、教师端 AI 生成、模型评估都可能要几十秒到几分钟，放进后台任务，不占用提问的处理能力。
6. **可观测**：每一步都有耗时和失败的指标，每次敏感操作都有审计记录，日志里不出现个人信息。
7. **一套 Docker 部署**：所有组件在一个 compose 里，一条命令启动（第 9 节）；但应用不在内存里保存只此一份的状态，以后真需要时可以多开几个 api 容器。

### 16.4 提问流程（v4）

| # | 步骤 | v3.1 | v4 的变化 |
|---|---|---|---|
| 0 | 进入流程前（API 层） | 登录检查 | 加课程角色检查（是否选了这门课）和用量检查（每个学生的频率和每天的额度） |
| 1 | `privacy_filter` | 一套固定规则 | 按课程类型加载**隐私档案**：基础层 + 学科档案 |
| 2 | `understand` | 识别知识点、问题类型 | 另外判断是**知识问题**还是**课程事务问题**（截止日期、评分方式） |
| 3 | `learner_context` | 按主题读学习状态 | 按课程读；带上教师给这个学生定的**学习计划**；课程事务问题跳过 |
| 4 | `analyze_route` | MiniLM + LR/SVM | 不变；ECE 课程上要评估，可能补训练数据（C5） |
| 5 | `retrieve` | 按主题检索 | 按"课程级资料 + 当前主题资料"检索；事务问题优先检索大纲和项目要求 |
| 6 | `route` | 本地 / 云端 | 加入课程设置："只用本地模型"、路由偏好（来自第四档评估） |

| 7 | `generate` | 本地 / 云端，云端关口 | 统一通过**模型网关**调用：可信本地连接可以收到原文；外部连接只能收到通过云端关口的请求，网关会再检查一次 |
| 8 | `restore` | 还原占位符 | 不变 |
| 9 | `verify` | 固定的检查项 | 检查项由隐私档案决定（医学课才有 `medical_safety`） |
| 10 | `attach_check` | 附一道检测题 | 课程事务问题不附 |
| 11 | `record` | 记录脱敏日志 | 另外记录用量计数和指标；不存原文（不变） |

### 16.5 主要数据表（PostgreSQL）

- **身份和权限**：
  - `account`：账号。v4 改为"用户名 + 可选学校邮箱 + 系统角色"，系统角色分系统管理员和普通用户。
  - `login_identity`：登录方式 + 该方式下的用户标识 → 账号。
  - `auth_session`：登录会话。
  - `course_member`：课程 + 账号 + 课程角色（教师 / 助教 / 学生）+ 不公开标记。
- **课程目录**：
  - `course`：课程代码、名称、学期、课程类型、状态。
  - `course_settings`：每门课一行，字段可为空（16.6）。
  - `topic`：主题。
  - `kc`、`kc_prerequisite`：知识点和依赖关系。
  - `check_item`、`misconception`：检测题和误解，都带草稿/审核状态和审核人。
  - `material`：资料，属于课程级或某个主题；记录文件在数据卷里的位置、扫描结果和索引状态。
  - `index_version`：每门课程检索索引的版本号。
- **学习者**：
  - `learner_state`：按课程 + 知识点，以及课程级的整体能力。
  - `learner_preference`：学习偏好。
  - `learning_plan`：教师定的学习计划。
  - `evidence_log`、`learner_misconception`：作答证据和误解，都带课程。
  - `consent`：知情同意，按课程记录，包括同意时的方案版本。
- **运行**：
  - `request_log`：脱敏后的请求日志，不含原文。
  - `usage_counter`：学生 + 课程 + 日期 → 提问次数、云端调用次数。
  - `job`：后台任务。
  - `audit_log`：谁在什么时候查看或修改了什么。
  - `model_endpoint`：模型连接，包括地址、模型名、可信级别、加密后的 API key、属于系统还是某门课。
  - `system_settings`：系统设置。
  - `config_history`：设置修改记录。
- **教师端 AI**：
  - `ai_draft`：生成的草稿，包括类型、内容、来源资料和状态。
  - `eval_run`：第四档评估的结果。

### 16.6 设置的分层

| 层 | 内容 | 谁能改 |
|---|---|---|
| 1. 代码常量 | 安全不变量：`log_raw_text=false`、必须开的检查项、识别器内部参数 | 只能改代码，要走代码审查 |
| 2. `config.yaml` | 默认值和**硬上限**（`limits` 段：排队、超时、用量、上传大小等） | 部署的人 |
| 3. 环境变量 / `.env` / Docker secrets | 数据库地址、API key、会话密钥 | 部署的人 |
| 4. `system_settings` | 默认模型连接、启用了哪些课程类型 | 系统管理员（网页） |
| 5. `course_settings` | 课程类型、可见性方案、只用本地模型、路由偏好、课程自己的模型连接、用量（第二步才开放） | 课程教师（网页） |

**取值规则**：从第 5 层往上找第一个有值的层，最后按第 2 层的硬上限截断。第 1 层不能被覆盖。

### 16.7 部署（见第 9 节）

- **一套 Docker Compose**：proxy、api、worker、db，加上可选的监控，一条命令启动（AWS 加拿大中部，或任何服务器）。
- **vLLM 单独部署**：不在 compose 里，应用通过 OpenAI 兼容 API 连接。
- **网络**：只有 proxy 对外开放 443；db 只在 Docker 内部网络里。
- **环境**：先在测试主机上部署；正式部署在课程结束后。
- **本地开发**：同一个 compose 的 dev 配置（Ollama 代替 vLLM，或接外部的 OpenAI 兼容地址）；测试保留 SQLite。
